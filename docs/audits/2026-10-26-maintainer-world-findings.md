## 1. [P2] A rejected PCV dependency is displayed as an authentication problem

**Impact.** An already connected player can have PCV permission yet see “An authenticated PCV permission is required for this control,” with Refresh and scene controls disabled. Reconnecting cannot repair an unsupported/missing PCV dependency. The interface conceals the distinction that is needed to diagnose this user's repeated disabled-tab reports.

**Cause.** [ui/app.js:1229](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/ui/app.js:1229) folds authentication, capability and permission into one boolean; [ui/app.js:1256](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/ui/app.js:1256) attributes every authenticated rejection to permission. The server actually keeps readiness and granted scopes separate: [server/lib/dispatcher.php:387](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/lib/dispatcher.php:387). Readiness intentionally returns false for missing/mismatched owner or core source: [server/adapters/pcv.php:438](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/adapters/pcv.php:438) and [server/adapters/pcv.php:392](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/adapters/pcv.php:392).

A concrete external trigger exists in the supplied host matrix. The real production `qd_pcv_stock_main_matches_pin()` accepts dev/current/unstable `main.php`, but rejects the 3.4.2 branch's `ef2ff9a5…` file. Its host still invokes preprocessing before the raw-event early exit: [server-beta342/main.php:201](https://github.com/Dwemer-Dynamics/HerikaServer/blob/d3945ecb65d4338a63978c81c3d9b09a936da585/main.php#L201). That source differs elsewhere too; this audit does **not** authorize adding its whole-file hash without reviewing the private-routing contract. Requirements currently say simply CHIM: [README.md:15](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/README.md:15). The defect here is misleading diagnosis, not the existence of source guards.

**Ran — browser plus actual PHP guard.** `node <artifact>/ui_probe.cjs` rendered the real UI in headless Edge. A control derived from the prior real-server full-access bootstrap retained `authenticated=true, access.pcv=true` and changed only `capabilities.pcv=false`. Result: envelope accepted, banner “Connected to CHIM,” false permission message, Refresh disabled, zero browser network requests. I inspected the screenshot. The browser's native bridge was controlled; no game or network authentication was performed. `php -n <artifact>/pcv_main_probe.php` executed the unmodified guard against the four raw official files: true/true/true/false. [ui-capability-results.json](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/ui-capability-results.json), [capability-diagnostic.png](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/capability-diagnostic.png), [pcv-main-results.json](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/pcv-main-results.json).

**Suggested fix.** Render separate states for not connected, permission denied and owner unavailable/unsupported. Preserve the guard and expose a bounded dependency reason; publish the tested host matrix. A dependency failure should point to the relevant owner/host requirement, not ask a permitted player to authenticate again.

## 2. [P2] The first profile read can wait indefinitely on a database lock

**Impact.** Opening/reconnecting/refreshing can stall behind a profile-table lock. A native HTTP deadline can expire while the PHP request still waits, making the game report connection failure although it reached the database. This is a reproduced failure mode, not a claim that it caused the user's earlier live failure.

**Cause.** [server/adapters/runtime_support.php:438](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/adapters/runtime_support.php:438) opens the host reader connection; [server/adapters/runtime_support.php:461](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/adapters/runtime_support.php:461) begins a read transaction and immediately calls `pth_state()` without setting a SQL lock or statement timeout. Bootstrap performs authoritative scope reads before and after readiness: [server/lib/dispatcher.php:387](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/lib/dispatcher.php:387), [server/lib/dispatcher.php:409](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/lib/dispatcher.php:409). MP/SAS's later 3000ms snapshot limits do not cover this earlier read: [server/adapters/mp.php:909](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/adapters/mp.php:909), [server/adapters/sas.php:334](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/server/adapters/sas.php:334).

The outside contract is explicit: [server-dev/lib/playthrough_preferences.php:23](https://github.com/Dwemer-Dynamics/HerikaServer/blob/0ec590b42c8087860138bb4e9aab470049ff9a2b/lib/playthrough_preferences.php#L23) sets `connect_timeout=3`, which limits connecting, not waiting for a relation lock. [server-dev/lib/playthrough_home.php:16](https://github.com/Dwemer-Dynamics/HerikaServer/blob/0ec590b42c8087860138bb4e9aab470049ff9a2b/lib/playthrough_home.php#L16) reads `chim_meta.playthrough_profiles`. The host's mutation path already demonstrates `SET LOCAL lock_timeout='2s'`: [server-dev/lib/playthrough_home.php:137](https://github.com/Dwemer-Dynamics/HerikaServer/blob/0ec590b42c8087860138bb4e9aab470049ff9a2b/lib/playthrough_home.php#L137). The bundled PCV identity reader also opens a connection before checking scene state and reaches `pth_state()` without SQL limits: [pcv-companion/private-conversation-v0.1.23/server/state.php:187](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/pcv-companion/private-conversation-v0.1.23/server/state.php:187); that additional route was read, not separately lock-timed.

**Ran — actual PostgreSQL15.14 and actual reader.** `wsl.exe -d DwemerAI4Skyrim3-test2 -u root -- /bin/bash <artifact>/run_db_probe.sh` created a new private cluster with no TCP listener. It called the unchanged Department reader and unchanged official `pth_state()` on a supplied scratch connection; it did not invoke `ptp_connect()` against its hard-coded default database. A second real session held ACCESS EXCLUSIVE on the profile table for1.8s. Default `statement_timeout=0, lock_timeout=0`: read accepted after **1754.38ms**. Control with connection option `lock_timeout=500ms`: refused after **500.798ms**. Baseline **2.851ms**. The observed default worst case has no finite SQL lock bound; the test released its lock deliberately. The configured500ms control behaved as bounded. [db-lock-results.json](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/db-lock-results.json), [db_probe.php](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/db_probe.php), [db_probe_driver.py](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/db_probe_driver.py), [db-cleanup.json](K:/ActorwrightExchange/artifacts/department-maintainer-audit-20261026/db-cleanup.json).

**Suggested fix.** Set bounded `SET LOCAL lock_timeout` and `statement_timeout` immediately after BEGIN, before the first profile query, on each owned reader transaction. Respect caller-owned transactions and restore fencing. Use the host's bounded transaction pattern. Keep the native deadline as an additional boundary, not the database cancellation mechanism.

**3b. The main build guide directs maintainers to an old installable — read.** [docs/BUILD.md:3](K:/ActorwrightExchange/projects/CHIM-DepartmentOfQuestionableDecisions/docs/BUILD.md:3) leads with a prealpha.12/13 recipe, `build-installable-prealpha13.py`, and says the normal install is `.13.zip` at line16. This matters because CHIM derives the requested version from the archive filename rather than choosing the greatest semantic version: [client-dev/Plugin/ServerPluginSync.cpp:194](https://github.com/Dwemer-Dynamics/CHIM/blob/5ca1bc361d1e11a3c58067599b494b1101c2c77b/Plugin/ServerPluginSync.cpp#L194) quotes `return left.last_write_time() > right.last_write_time();` then `archive.path().stem().string()`. The leading recipe is therefore not a reproducible instruction for the current candidate, and its “normal installation” filename is obsolete. Fix by putting the current .17 incremental command and its inputs first, with the old full-build recipe explicitly historical. No DLL rebuild is required to fix the guide.
